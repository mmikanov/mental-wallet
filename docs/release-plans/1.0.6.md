## Pre-review testing (test attribution WITHOUT submitting to review)

You can validate 1.0.6 on both stores' test tracks without releasing to the public / without
going to review. The two platforms behave very differently for attribution — this is by design,
not a build limitation:

### Android — Internal testing track: full, real attribution test ✅

The Play Install Referrer is delivered for any install that comes **through the Play Store**,
and the **Internal testing track counts**. So Android attribution can be verified end-to-end
before any production release:

1. Build and upload to the **Internal testing** track (`eas build --platform android`, then
   submit/upload to that track — do NOT promote to production).
2. Install as a tester via a **tagged link**, either:
   - landing page: `https://mentalhealthwallet.productsforgood.co/?utm_source=reddit` → tap the
     Google Play badge (the badge forwards the tag), or
   - direct: `https://play.google.com/store/apps/details?id=com.mentalwallet.app&referrer=utm_source%3Dreddit`
3. Install on a **real device or a Play-enabled emulator** (needs Google Play services — a bare
   emulator will NOT deliver the referrer).
4. Open the app, let it send a few events, then check the operator dashboard `/details/channels`
   — the install should appear under **reddit**; an untagged install should land in **organic**.

> **Fresh-install caveat:** the referrer is tied to a *new* install. If the device already has
> the app, fully **uninstall first**, then install via the tagged link, or Play returns the
> prior/empty referrer.

### iOS — TestFlight: build sanity-check only, NOT the channel signal ❌

This is a platform reality, not a track limitation:

- iOS has **no install-referrer API**; our app ships a **no-op on iOS** (reads nothing
  device-side), so there is no on-device channel to exercise on any iOS track.
- iOS channel attribution comes from **App Store Connect source analytics + the `ct=` campaign
  token**, read in the App Store Connect console — not from the app, not on our dashboard.
- **TestFlight installs do NOT flow through the public App Store listing**, so they generate no
  App Store Connect "Sources" / campaign-token analytics either.
- What TestFlight **can** confirm: the build runs, no new UI appeared (attribution is
  invisible), and events still flow — i.e. the iOS no-op does no harm.

### Recommended approach for 1.0.6

- Ship **Android to Internal testing now** and run the Task 15 attribution check there.
- Keep **iOS in TestFlight** purely as a "does it run / no regressions" check (there is no
  on-device iOS channel to test).
- Promote both to production together once Android attribution is confirmed. Real iOS channel
  data only ever appears in App Store Connect **after a public App Store release** (Task 16,
  post-launch).

## Known risks / notes

- **Attribution is directional, not exact** (a reinstall can look like a new person); it is a
  group-level signal for comparing channels. iOS is coarser than Android. These caveats are
  already surfaced on the operator dashboard.
- **No OTA for app content** — the attribution read only reaches users in an installed build;
  existing installs never backfill a channel (they stay organic).
- **Privacy unchanged** — the channel is a non-personal label on already-anonymous analytics;
  nothing new is collected and nothing is written to the messaging (PII) store.
- **Follow-up (non-blocking):** the per-channel retention query applies the phase window
  slightly differently than the headline cohort metric — safe, worth tidying for exact parity.
- **Separately:** the operator dashboard itself has a pending improvement spec
  (`.kiro/specs/attribution-dashboard-enhancements/`) — presentation-only, deploys with the
  analytics worker, independent of any app release.
