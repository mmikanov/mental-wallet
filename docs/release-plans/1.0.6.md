# Release Plan — 1.0.6

> **Read this first.** Most of what was built this cycle is **backend/worker/website** that has
> **already deployed independently** and is **live now** — it did not need an app release. The
> only thing that needs an actual app build is one unfinished piece (channel attribution Phase
> 4, the Android install-referrer read). See "What needs an app build" below. **You may not need
> to cut 1.0.6 at all until that piece is built.** The last shipped app version was 1.0.5
> (live on both stores); `app.json` currently reads 1.0.5 and bumps to 1.0.6 when this release
> is cut.

## Target

- **Version:** 1.0.6
- **Platforms:** iOS (App Store) + Android (Google Play)

## What needs an app build (go / no-go for 1.0.6)

**If channel-attribution Phase 4 is NOT yet built, there is no app-code change to ship, and
1.0.6 does not need to be cut.** Everything else this cycle is already live via worker/website
deploys.

Cut 1.0.6 only once Phase 4 (Android install-referrer read + event stamping) is implemented and
verified. At that point 1.0.6 carries:

- The Android install-referrer read + write-once channel storage + event stamping (the only
  user-facing-adjacent change — and it's invisible: no UI, no onboarding change).
- iOS ships the no-op (iOS has no device-side referrer; iOS attribution stays coarser, read
  from App Store Connect + time windows).

## Pre-build steps (when 1.0.6 is cut)

Follow the full checklist in `.kiro/steering/release-checklist.md`. Specifically:

1. **Version is already at 1.0.5 in `app.json`.** Bump to 1.0.6 with the one-command script
   (do NOT hand-edit): `npm run set-version -- 1.0.6`. This writes all four places (app.json,
   iOS Info.plist + pbxproj MARKETING_VERSION, android build.gradle versionName) and package.json.
   Build numbers auto-increment via EAS.
2. **Confirm the working tree is committed and pushed** so the build reflects intended code.
3. **Prepare release notes** for both stores in `docs/store-listing-copy.md` (add a 1.0.6
   entry). Diff since the last release tag to see what landed: `git log v1.0.5..HEAD`.
   - Note the Apple copy rule: never mention Android or any third-party platform in Apple
     "What's New" / metadata.
   - User-visible content of 1.0.6 is minimal (the attribution read is invisible). Frame
     release notes around any genuinely user-facing change; if none, a short "reliability and
     behind-the-scenes improvements" note is honest.

## Build & submit

4. `eas build` (both platforms), then `eas submit` per the checklist.
5. Set the "What's New" / release notes in **App Store Connect** and **Google Play Console**
   (not automated by EAS).
6. Confirm the correct build/versionCode is selected in each console before final submit.
7. **iOS App Review notes:** the attribution read adds no new deep-link or WebView surface and
   transmits no user data — it reads the install referrer and attaches an anonymous channel
   label to existing anonymous analytics. State that in App Review Information.

## After submitting

8. Tag the release commit: `git tag -a v1.0.6 <commit> -m "Release 1.0.6 — <summary>"` and
   `git push origin v1.0.6`.
9. Android rollout safety: the production track currently publishes to 100% with no manual gate
   — consider a staged rollout (see `docs/deployment/app-deployment.md`).

## Verification

- **Already-live pieces:** verified at the unit/deploy level and smoke-tested on the live
  workers/site (health checks, endpoint wiring, served markup). The honest caveats stand:
  - the operator dashboard channel breakdown reads correctly against (currently all-organic)
    data; a live visual check needs the dashboard secret;
  - the daily summary email's actual inbox delivery is only provable on a real cron run with
    eligible subscribers;
  - landing-page tag forwarding is unit-tested; the JS href rewrite is browser-runtime.
- **Phase 4 (when built):** the Android install-referrer read is a **native install-time
  signal** — it cannot be proven by unit tests. Verify on a real device/emulator with an
  internal-track build: install via a tagged link and confirm the install's events arrive with
  the expected `channel`, and that an untagged install lands in organic. iOS attribution is
  confirmed in App Store Connect, not on-device.

## Known risks / notes

- **Attribution is directional, not exact** (a reinstall can look like a new person); it is a
  group-level signal for comparing channels. iOS is coarser than Android. These caveats are
  already surfaced on the operator dashboard.
- **No OTA for app content** — the attribution read only reaches users in an installed build;
  existing installs never backfill a channel (they stay organic).
- **Privacy unchanged** — the channel is a non-personal label on already-anonymous analytics;
  nothing new is collected and nothing is written to the messaging (PII) store.
- **Follow-up (non-blocking):** the per-channel retention query applies the phase window
  slightly differently than the headline cohort metric — safe, worth tidying for exact parity.
- **Separately:** the operator dashboard itself has a pending improvement spec
  (`.kiro/specs/operator-dashboard-enhancements/`) — presentation-only, deploys with the
  analytics worker, independent of any app release.
