# Design Review — 1.0.6 Bug Fixes

Reviewed: `.kiro/specs/1.0.6-bug-fixes/design.md` against `.kiro/specs/1.0.6-bug-fixes/requirements.md`.
This was a design-only task; no code changes were expected or checked for.

**Verdict: APPROVED** (0 HIGH, 0 MEDIUM, 3 NIT).

The design is unusually well-grounded: its "confirmed in code" claims hold up against the
actual source in every case I checked. All four bugs are covered, the traceability table maps
every acceptance criterion, both deferred decisions (Bug 1 in-app rendering, Bug 4
exclude-vs-label) are explicitly made and justified, Bug 3 is a genuine instrumentation plan
rather than a speculative fix, and the deploy section correctly separates the app-build parts
from the independently-deployed website/worker parts. The findings below are all NITs — worth
tightening in `tasks.md`, but none block.

  Bug 2 (create-tool deep link), Bug 3 (archived-tool reminder), Bug 4 (unsubscribed mislabeled

  Spot-checked: 1.6 → Deliberate Per-Surface Exceptions, 3B.2 → "preserved by current archive
  path; confirmed", V.3 → Bug 2 Testing Strategy. No orphan criteria.

  It names the native view (`TipDetailScreen`), the body-rendering approach (store raw markdown
  in the index, render with `react-native-markdown-display` — new pinned JS-only dependency),
  and the `TipsFeedScreen.openTip` change (navigate instead of `WebBrowser.openBrowserAsync`).
- **Bug 2 create-tool route** — yes. Adds `CardCreator: 'create-tool'` to `linking.ts`
  `config.screens` (both `mentalwallet://create-tool` and `/app/create-tool` via the shared
  prefixes), points the tip CTA at `/app/create-tool`, adds a `create-tool` entry to
  `website/app-fallback.html`'s `ROUTE_COPY`, and keeps in-app native nav consistent via the
  shared `tipCtaToNavigation` mapper. The route-parse-unit-testable vs. on-device caveat (V.3)
  is stated.
- **Bug 3 is an instrumentation plan** — yes. It is explicitly not a blind fix: a table of
  specific `__DEV__` logs with their exact locations and the smallest question each answers, a
  build-marker to rule out a stale build, how to read them on-device, and a decision tree from
  log output to the matching conditional fix. It states "No fix is written in this design" and

- **Bug 4 reporting-accuracy only** — yes. The design confirms `sendTipEmail`/`sendOneDrip` are

## Findings

### NIT 1 — `runDripPass`'s existing `|| !resolved.campaign` fallthrough should be called out for the new `unsubscribed` kind

In §Bug 4 "Classification Change," the design says `runDripPass` will "add an `unsubscribed`
counter and emit `status: 'unsubscribed'` plan entries." That is correct, but the existing
dispatch in `runDripPass` (confirmed in `messaging-worker/src/index.ts`) is:

```ts
if (resolved.kind === 'waiting' || !resolved.campaign) {
  waiting++;
  plan.push({ email: sub.email, status: 'waiting', ... });
  continue;
}
// kind === 'next' → attempts a send
```

If the implementer adds the `unsubscribed` kind to `resolveNextForSubscriber` but does NOT add
an explicit `unsubscribed` branch **before** this `waiting` check, an `unsubscribed` result
(which carries a `campaign`) would fall through the `waiting`/`!campaign` condition and land in
the `kind === 'next'` send path — the opposite of the intended fix. The design's prose implies
the new branch but doesn't flag this ordering hazard.

**Fix:** In `tasks.md`, make it explicit that the new branch must come first, e.g.:

```ts
if (resolved.kind === 'unsubscribed') {
  unsubscribed++;
  plan.push({ email: sub.email, status: 'unsubscribed', campaign_id: resolved.campaign?.id, ... });
  continue;
}
if (resolved.kind === 'waiting' || !resolved.campaign) { ... }
```

Also note the `|| !resolved.campaign` case (missing-campaign) currently collapses into
`waiting`; leave it in `waiting` (it is genuinely not an unsubscribe), which the ordering above
preserves.

### NIT 2 — `SummaryPlanEntry.status` already has a `not_yet` member the design doesn't mention

The design (§Bug 4, `dripSummary.ts` bullet) says it will "extend `SummaryPlanEntry.status` to
include `'unsubscribed'`." The actual type today is
`'next' | 'waiting' | 'finished' | 'not_yet'` (confirmed in `dripSummary.ts`) — there is an
existing `not_yet` member (used by the time-travel simulation for subscribers who hadn't signed
up yet on the simulated day) that the design omits from its description. This doesn't change the
plan, but an implementer reading the design might assume the union is `next|waiting|finished`
and accidentally drop `not_yet` when editing.

**Fix:** In `tasks.md`, note the union is currently
`'next' | 'waiting' | 'finished' | 'not_yet'` and the change is purely additive
(`... | 'unsubscribed'`), and that `not_yet` behavior is unchanged.

### NIT 3 — the tip's `version` bump (Bug 2) does not reach the drip/website via `index.json`

§Bug 2 says to bump `content/tips/add-your-own-tool.md` frontmatter `version: 3 → 4` "per the
card/content-versioning convention … the number the website build and the drip read." Verified
in `website/build-content.js`: `parseTip` does parse `version`, but the emitted
`content/index.json` `index` mapping does **not** include `version` (fields are slug, title,
summary, type, topics, heroImage, cta, url, publishedAt). So neither the worker (`fetchTipIndex`
/ `ContentIndexEntry`) nor the app actually consume a tip `version` today — the bump is a
source-of-truth hygiene marker, not something the drip "reads." The design's parenthetical
slightly overstates its runtime effect.

**Fix:** Keep the version bump (it's the right convention), but correct the rationale note:
the bump documents the content change in the single source; it has no runtime consumer in the
drip/website path unless `version` is also added to the `index.json` mapping (not required for
these fixes). Optionally add `version` to the index map if you want it consumable later — but
that is out of scope for 1.0.6.

## Verified Assumptions

The following design claims were checked against the actual source and are **correct**:

1. **`website/build-content.js` parses the full body but omits it from the index.** `parseTip`
   produces `tip.body = body.trim()` and `renderArticle` uses `marked.parse(tip.body)`; the
   `index` mapping emits slug/title/summary/type/topics/heroImage/cta/url/publishedAt with **no
   `body`**. Adding `body: t.body` to that map is the correct, minimal producer change. ✓
2. **The worker's `ContentIndexEntry` lacks `body`, but `parseTip` and `sendTipEmail` already
   handle a body.** `ContentIndexEntry` is `{ slug, title, summary, heroImage?, cta? }` (body
   "intentionally absent" per its comment); `TipPayload` has `body?: string`; `parseTip` already
   maps `body` when present; `sendTipEmail` already renders `bodyHtml`/`bodyText` from
   `tip.body`. So the email becomes full-body with only the pass-through change the design
   describes. ✓
3. **The email compliance wrapper is untouched by a body change.** `sendViaResend` sets the
   `List-Unsubscribe`/`List-Unsubscribe-Post` headers and `sendTipEmail` renders the
   Manage-preferences / Unsubscribe footer and the "Cheers, Moshe / Products for Good"
   signature independently of `body` (Req 1.7). ✓
4. **The in-app feed opens the website article in an in-app browser.** `TipsFeedScreen.openTip`
   calls `WebBrowser.openBrowserAsync(resolveTipUrl(tip))`; the header comment states "The app
   never renders tip bodies." `Tip` (via `tipsService.parseTip`) has no `body`. The native-render
   decision and the `parseTip` body-map change are correctly scoped. ✓
5. **`CardCreator` exists in `RootStackParamList`** (`{ cardId?, adminEditCardId?,
   adminEditSource? } | undefined`), so `CardCreator: 'create-tool'` resolves to a real screen,
   and new-tool mode = no params matches `WalletScreen`'s create-tool navigation. ✓
6. **`linking.ts` has no `create-tool` route; `add-tool` → `LibraryBrowser`.** `config.screens`
   lists only `MainTabs/Wallet`, `LibraryBrowser: 'add-tool'`, `Archive`, `Settings`. The
   `getStateFromPath` `default` case calls `defaultGetStateFromPath(withoutApp)`, so a bare
   `create-tool` path needs no special-case once `CardCreator: 'create-tool'` is registered —
   exactly as the design claims. ✓
7. **The tip CTA currently points at `/app/add-tool`, `version: 3`.** Confirmed in
   `content/tips/add-your-own-tool.md` frontmatter. ✓
8. **`website/app-fallback.html` `ROUTE_COPY` has no `create-tool` and falls back to `wallet`.**
   Map has `wallet`, a learn-more entry, `add-tool`, plus an apps-filter variant; unmapped routes
   `return ROUTE_COPY[route] || ROUTE_COPY['wallet']` — so an un-mapped `create-tool` would show
   "Open your wallet," which is why the new entry is needed (Req 2.3). ✓
9. **`docs/deployment/deep-links.md` Routes table + Tip CTA mapping exist as described**, with
   `add-your-own-app, add-your-own-tool → /app/add-tool`. The design's doc-update plan (add a
   `create-tool` row, move `add-your-own-tool`) matches the real file. ✓
10. **Bug 3 code claims all hold.** `cardService.archive(id)` commits, then calls
    `createReminderService().disableForCard(id)` in a `try/catch` that swallows with a
    "Non-fatal" comment. `disableForCard` selects `WHERE card_id = ? AND is_active = 1`, calls
    `cancelNotificationIds` per row, then `UPDATE reminders SET is_active = 0 WHERE card_id = ?`.
    `cancelNotificationIds` → `parseNotificationIds` (handles JSON array or single string) →
    `cancelScheduled(id).catch(() => {})` (swallowed). `reconcileRemindersOnLaunch` selects
    `WHERE is_active = 1` and reschedules only when stored ids are missing from
    `getAllScheduledNotificationsAsync()`. Every instrumentation point in the design's table maps
    to a real seam. ✓
11. **Bug 4 root cause is exactly as quoted.** `resolveNextForSubscriber` returns
    `{ kind: 'waiting', campaign }` when `!scopeOptedIn`, and `runDripPass` counts that as
    `waiting++` with a `status: 'waiting'` plan entry; `buildDripSummary` renders it under the
    Waiting total. The `resolveNextForSubscriber` return type is
    `{ kind: 'next' | 'waiting' | 'finished'; campaign?: CampaignRow }` (worker-local, distinct
    from `drip.ts`'s pure `NextStepResult` which is `next | waiting | finished`). The design's
    claim that the new `unsubscribed` kind belongs at the worker return type (not in the pure
    `resolveNextStep`) is correct. ✓

## Unverified / Wrong Assumptions

- **`react-native-markdown-display` builds cleanly under Expo SDK 54 / RN 0.81 New
  Architecture** — the design itself flags this as an open question for tasks ("JS-only,
  expected fine; verify at task time"). Not independently verified here; it is correctly parked
  as a task-time check, not asserted as fact. (Not a finding — the design is honest about it.)
- **The on-device behaviors** (real email matching across surfaces, native deep-link cold open,
  OS repeating-notification firing after archive) are, by the design's own admission, not
  provable by the unit layer and require a device/real-run pass. Correctly labeled as caveats
  (V.1, V.3, V.4). (Not a finding.)
